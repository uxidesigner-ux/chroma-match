# 게임판 공간 최적화 — 2026-10-04

사용자 요청: 첨부한 모바일 페이퍼 화면의 이상한 점을 찾고, 화면에 맞게
최적화하여 게임판을 더 크게 표시한다. 구현과 검증 범위이며, 이번 요청으로
라이브 배포까지 수행하지 않는다.

## 관찰 / 문제

현재 라이브 진입 파일 `index-B4SiKopv.js`와 원격 main / 로컬 기준 커밋
`4aecc6af3aa81606c4cd26137edae248fe2e6cc0`을 확인했다. 깨끗한 체크아웃에서
수정 전후 격리된 Chromium 게스트로 실제 렌더링과 DOM 크기를 비교했다.
Firebase와 선택적 VRM 로딩은 차단했다. 사용자 계정이나 저장 게임은 건드리지
않았다. 이미지의 물리 해상도를 CSS 화면 크기로 단정하지 않고, 390px 폭과
650–844px 사용 가능 높이를 각각 재현했다.

- 목표 라벨이 한 줄이어도 2.7em을 예약하고, 목표 단위를 별도로 반복한다.
- 단계와 진행률이 두 줄을 쓰며, 효과 48px와 아이템 안내 32px를 따로 비워 둔다.
- 바깥/게임/보드의 중복 여백, 50–60px 도구와 하단 안내 슬롯이 높이를 소비한다.
- 390×700에서 보드는 280×420px인데 실제 보이는 높이는 약 336px여서 끝 행이
  잘린다. 단순히 폭을 늘리면 보드 높이도 함께 늘어 잘림이 더 심해진다.
- 새 안내 위치에서 페이퍼의 노란 안내색은 배경과 구분이 약하다.

조사되지 않은 이용자 특성/사용성 점수는 주장하지 않는다. 실제 과제는 목표와
남은 횟수를 읽으면서, 가려지거나 움직이지 않는 보석을 조작하는 것이다.

## 선택한 설계 / 완료 기준

- 목표 / 반응하는 프로필 / 이동 횟수의 3등분은 유지한다.
- 한 줄 목표는 실제 한 줄만 사용한다. 숫자의 전체 접근성 라벨에 단위를
  유지하고, 한국어/일본어/중국어 점수 목표도 라벨 자체에 점수임을 명시한다.
- 단계와 진행률을 한 줄로 묶는다. 점수와 best를 다시 추가하지 않는다.
- 효과, 아이템 조준 안내와 첫 사용 안내는 한 고정 48px 공간을 공유한다.
  아이템 안내는 대기 중 합체 힌트보다 먼저, 실제 연쇄/합체 결과는 안내보다
  먼저 보인다. 결과가 끝나면 조준 안내가 복귀한다. 보드 위에 덮지 않는다.
- 안내를 본문색과 600 두께로 읽기 쉽게 표시한다. 새 색/폰트/의존성은 없다.
- 하단 버튼은 48px, 짧은 화면은 44px로 통일하고 8px 간격을 둔다. 모든 터치
  영역은 최소 44×44px이며, 나가기 버튼은 오른쪽 끝에 유지한다.
- 전화기 프로필은 80px, 사용 가능 높이 700px 미만에서는 64px, 넓은 화면은
  112px를 사용한다. 상단은 12px/OS 안전 영역과 최대 반응 모션을 확보한다.
- 남은 공간에서 6:9 비율의 **전체 9행이 들어가는 최대 크기**를 사용한다.
  매우 짧은 화면에서는 44px 보석을 줄이지 않고 기존 명시적 행 이동을 유지한다.
- 메시지 등장/소비로 보드 위치나 크기가 바뀌지 않는다. viewport offset,
  클래식 스크롤바, 폴드 힌지, 200% 글자, 키보드, 감소 모션을 보존한다.
- 6×9 퍼즐, RNG, 점수/아이템 소비, 리플레이와 저장 형식은 바꾸지 않는다.

`impeccable`의 product/layout 기준으로 중복 높이를 통합하고 중요한 과제와
44px 터치 영역을 우선했다. 공통 `USER_EXPERIENCE_QUALITY_PLAYBOOK_KO.md`는
이 워크스페이스에서 발견되지 않아, 제공된 AGENTS 지침과 PRODUCT의 검증
기준을 적용했다. 별도 디자인 시스템이나 UI 전면 재작성을 도입하지 않았다.

## 실제 크기 비교

동일한 Paper / 한국어 / 62단계 / 목표 14,000 / 이동 65의 **콘텐츠 fixture**다.
게임을 실제로 62단계까지 진행했다는 증거가 아니다. CSS px, 오버레이 스크롤바
환경의 실측이며, OS 안전 영역과 글자 설정에 따라 값은 달라진다.

| 사용 가능 화면 | 이전 보드 폭 | 수정 보드 폭 | 보드 면적 증가 | 수정 후 9행 |
| --- | ---: | ---: | ---: | --- |
| 390×650 | 280 | 280.41 | 약 0% | 전부 표시. 보이는 높이는 286 → 421 |
| 390×700 | 280 | 296.41 | 약 12% | 전부 표시 |
| 390×760 | 280 | 336.41 | 약 44% | 전부 표시 |
| 390×844 | 300.67 | 374 | 약 55% | 전부 표시 |
| 430×932 | 359.34 | 414 | 약 33% | 전부 표시 |
| 1280×800 | 280 | 341.73 | 약 49% | 전부 표시 |

320×568은 물리적으로 전체 9행을 44px로 넣기 어렵다. 폭은 280px로 유지하고
보이는 높이를 약 233 → 339px로 늘렸다. 스크롤 버튼으로 나머지 행을 보며,
일반 페이지가 당겨지거나 보드가 터치 순간 움직이지 않는다.

## 검증 중 발견한 문제 / 수정

- 상단 8px 실험에서는 프로필 최대 반응 때 링이 화면 위로 0.6–2px 벗어났다.
  상단을 12px로 돌리고 짧은 HUD 내부 패딩만 조정하여 모션 여유를 보존했다.
- 창 크기가 먼저 바뀌고 resize 이벤트와 shell 프레임은 늦게 오는 순간에는
  캔버스 사각형만 비교하는 입력 코드가 이전 드래그를 받아들였다. 강제로
  그 시간차를 재현하면 이동 25 → 24로 실패했다. 포인터 시작 시의 창/visible
  viewport 크기·offset·scale도 비교해서 취소한다. 이후 정상 교환은 유지한다.
- 기존 부분 행 키보드 검사는 568px 높이에서 마지막 행이 이미 보이는데도
  더 스크롤할 것을 요구했다. 같은 검사만 500px 높이로 옮겨 실제로 잘린 행의
  접촉/행 안내/키보드 스크롤을 계속 검증한다. 목표·최소 크기는 낮추지 않았다.
- 힌지 검사는 전후 모두 `stack`인 속성을 기다려 실제 400px pane 업데이트
  전에 1280px 이전 사각형을 읽었다. 실제 app 폭이 400px이 될 때까지 검사한다.

## 검증 / 증거

- 타입 검사와 Pages 경로 프로덕션 빌드 통과.
- 전체 단위 검사 **223개 통과**.
- 게임 안정화/반응형/새 공간 회귀 브라우저 검사 **40개 통과**. 12개 기존 크기,
  5개 모바일 공간 크기 × 3개 테마 × 4개 언어, 전체 목표/큰 숫자, 정상/감소
  모션, 200% 텍스트 토큰, 터치, 키보드, 아이템 소비, 일시정지/종료/다시 플레이,
  viewport offset/핀치/힌지를 포함한다.
- 최종 안내색 변경 뒤 새 공간/상태 검사 **4개 재검사**와 프로덕션 게임 검사
  **3개 재검사 모두 통과**. 후자는 개발용 game hook 없이 실제 아이템/연쇄/
  키보드 플레이와 390×650/844 전체 행, DPR3 효과·접촉을 확인한다.
- `git diff --check` 통과. 코드 diff와 실제 캡처를 교차 검토했다.
  별도 독립 리뷰어는 사용하지 않았다.

수정 전 크기, 중간 실패 trace, 입력 타이밍 수정 전 실패, 최종 크기/캡처와
Playwright 결과는 `/tmp/chroma-board-layout.ApcZFv/`에 있다. 재현 가능한 새
기준은 `tests/studio/game-space.spec.ts`와 강화된 release 테스트에 남겼다.

## 남은 범위

물리 iOS Safari / Android WebView / 폴드 센서 / 스크린리더 실사용은 확인하지
않았다. 제어된 visualViewport와 모바일 터치 에뮬레이션을 기기 검증으로
표현하지 않는다. 게임 외 3D 편집기/로비의 전체 브라우저 스위트를 다시 실행한 것은 아니며,
모델/에셋/로비 동작은 변경하지 않았다. 기존 500kB 초과 번들 경고도 남는다.
라이브 사이트는 기준 커밋을 유지하며, 새 변경은 로컬 `codex/game-board-space`
브랜치에만 있다. 라이브 반영은 별도 요청 후 전체 배포 게이트를 통과해야 한다.
